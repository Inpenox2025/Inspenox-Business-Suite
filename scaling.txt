### 1. How Many Users Can Log In at a Time?

- **Stateless Architecture**: Your login system (`api/auth.js`) does not keep open server sockets or memory sessions. It verifies credentials against Postgres and returns user details which are saved in the browser's `localStorage`.
- **Active Logged-In Sessions**: **Unlimited**. 500 agents can stay logged in simultaneously because idle users consume 0 requests and 0 server memory.
- **Simultaneous Login Spike (Instant Burst)**:
  - If 50–100 agents submit the login form at the exact same second, Cloudflare Pages Functions easily handles it (Cloudflare Free allows **1,000 requests per minute**).
  - Because Neon connects via `@neondatabase/serverless` over stateless HTTP rather than persistent TCP sockets, it won't crash from connection pool exhaustion.

### 3. How to Scale 10x for FREE (Code-Level Optimizations)

You can increase your free tier capacity from 14 agents to **80+ agents without paying anything** by making 3 quick code improvements:

#### A. Pause Polling When the Browser Tab Is Hidden
Currently, if an agent switches tabs, minimizes Chrome, or leaves their computer, the 4-second polling keeps firing. Add Page Visibility detection to `controllers/inboxController.js`:
```javascript
document.addEventListener('visibilitychange', () => {
    if (document.hidden) {
        // Stop polling when tab is in background
        if (inboxPollInterval) clearInterval(inboxPollInterval);
    } else if (activeCustomer) {
        // Resume polling immediately when tab comes back into focus
        fetchChatMessages();
        inboxPollInterval = setInterval(fetchChatMessages, 4000);
    }
});
```

#### B. Adaptive / Smart Polling Backoff
If no new messages have arrived in the last 60 seconds, slow the polling down from 4s to 12s. Reset back to 4s the moment a new message is sent or received:
```javascript
// Dynamic interval: 4s when actively typing/receiving, 12s when idle
let idleRounds = 0;
async function fetchChatMessages() {
    // ... fetch logic ...
    if (newMessagesFound) {
        idleRounds = 0;
        setPollSpeed(4000);
    } else {
        idleRounds++;
        if (idleRounds > 10) setPollSpeed(12000); // Back off after 40s of inactivity
    }
}
```
> **Impact:** This alone saves **60% to 70%** of your daily request quota.

#### C. Edge Caching for Static Endpoints
Endpoints like `/api/templates`, `/api/tags`, and `/api/config` rarely change. Add caching headers in `lib/cf-adapter.js` for GET requests:
```javascript
res.setHeader('Cache-Control', 'public, max-age=60, s-maxage=300, stale-while-revalidate=600');
```

### 5. Where & How to Implement Rate Limiting for Better UX

Rate limiting should be applied at three layers: **Cloudflare Edge**, **API Backend Middleware**, and **Frontend Client Debounce**.

```
User Action (Click / Polling)
        │
        ▼
[ Layer 1: Frontend Debouncing ]   ──> Prevents accidental double-clicks & spam
        │
        ▼
[ Layer 2: Cloudflare Edge WAF ]   ──> Blocks DDoS & brute-force before touching server
        │
        ▼
[ Layer 3: API Middleware ]        ──> Returns HTTP 429 with Retry-After for UX toasts
```

---

#### Layer 1: Frontend Debouncing & Button State (Immediate UX)
Prevent users from accidentally triggering multiple WhatsApp broadcasts or duplicate message sends:
In `controllers/inboxController.js` and `controllers/broadcastController.js`:
```javascript
async function sendChatMessage() {
    const sendBtn = document.getElementById('chat-send-btn');
    if (sendBtn.disabled) return; // Prevent double-trigger

    try {
        sendBtn.disabled = true;
        sendBtn.classList.add('opacity-50', 'cursor-not-allowed');
        
        await apiCall('/api/send-message', { ... });
    } catch (err) {
        if (err.status === 429) {
            showToast('⚠️ Slow down! Please wait a few seconds before sending another message.', 'warning');
        } else {
            showToast('Failed to send message: ' + err.message, 'error');
        }
    } finally {
        sendBtn.disabled = false;
        sendBtn.classList.remove('opacity-50', 'cursor-not-allowed');
    }
}
```

#### Layer 3: Backend API Middleware (In Code)
For endpoints with business constraints (such as Meta WhatsApp Cloud API throughput limits or chat polling), you can add a lightweight in-memory rate limiter right in `functions/api/[[path]].js` or `lib/cf-adapter.js`:

```javascript
// In-memory bucket per edge instance
const rateLimitMap = new Map();

function checkRateLimit(ip, endpoint, limit = 60, windowMs = 60000) {
    const key = `${ip}:${endpoint}`;
    const now = Date.now();
    const entry = rateLimitMap.get(key) || { count: 0, resetAt: now + windowMs };

    if (now > entry.resetAt) {
        entry.count = 1;
        entry.resetAt = now + windowMs;
        rateLimitMap.set(key, entry);
        return { allowed: true, remaining: limit - 1, resetIn: Math.ceil(windowMs / 1000) };
    }

    entry.count++;
    if (entry.count > limit) {
        return { 
            allowed: false, 
            remaining: 0, 
            resetIn: Math.ceil((entry.resetAt - now) / 1000) 
        };
    }

    return { allowed: true, remaining: limit - entry.count, resetIn: Math.ceil((entry.resetAt - now) / 1000) };
}
```

When a rate limit is exceeded, return clean headers that the frontend can read:
```javascript
const rateCheck = checkRateLimit(clientIp, routeName, 30, 60000); // 30 req/min
if (!rateCheck.allowed) {
    return new Response(
        JSON.stringify({ 
            error: 'Too Many Requests', 
            message: `Please wait ${rateCheck.resetIn} seconds before retrying.` 
        }),
        { 
            status: 429, 
            headers: { 
                'Content-Type': 'application/json',
                'Retry-After': String(rateCheck.resetIn) 
            } 
        }
    );
}
```
